# 声音断续与游戏性能排查

串流设置里的 60 fps 是视频输出目标，不等于模拟器已经按原速运行。判断声音卡顿时，要分开检查游戏模拟、音视频编码、网络传输和浏览器播放。

## 先确认本次会话的实际设置

进入本人头像 → **用户设置 → 画面设置**，查看“当前会话”尺寸。分辨率按玩家和当前浏览器设备分别保存，只在下次启动云游戏时应用；仍在运行的 720p 会话不会因保存 1080p 或换到另一台设备继续游戏而改变。模拟器内部的渲染倍率是另一项设置，不能用串流尺寸推断。

也可只读查看当前玩家的 `GET /p/playerN/api/settings/display?device_id=<设备UUID>` 和 `GET /p/playerN/api/session`。不传 `device_id` 时返回玩家默认值；设备标识保存在当前网站的 `retroone:display-device` 本地存储项中。排查无需结束游戏或重新启动模拟器。

## 区分瓶颈

| 现象或证据 | 优先检查 |
| --- | --- |
| 模拟器主线程占满一个核心，游戏速度也下降 | CPU 单线程性能、散热和调度；整机 CPU 总占用低不能排除这个瓶颈 |
| 温度接近限制，热降频计数持续增长 | 风扇、通风、散热接触及主机负载 |
| 游戏模拟正常，但编码器报错或画面丢帧 | GPU 驱动、采集与编码负载、同时运行的会话数量 |
| 服务器正常，换网络或客户端后明显不同 | 网络抖动、接收缓冲、浏览器解码与音频播放状态 |
| 卡顿集中在首次进入新场景 | 结合帧时间、着色器编译与磁盘等待记录判断，不能只凭感觉认定原因 |

Intel 的 `coretemp` 温度输入使用毫摄氏度。温度上限取决于 CPU 型号，不能给所有主机套用同一条阈值。[Linux coretemp 文档](https://docs.kernel.org/hwmon/coretemp.html)

支持相关接口的 Linux 主机，可在 `/sys/devices/system/cpu/cpuN/thermal_throttle/` 读取降频计数及累计时间。应比较同一 CPU 两次采样的增量；单次历史计数不代表当前仍在降频，同一封装下不同逻辑 CPU 的包级计数也不能相加。[Intel 热降频计数说明](https://cdn.kernel.org/doc/html/latest/admin-guide/thermal/intel_thermal_throttle.html)

## 一次实际排查的边界

在 i7-1255U 主机的一次 3DS 游戏测试中，模拟器主线程连续三次采样占用单核约 99%～100%；CPU 包温达到 100°C，10 秒内包级热限制累计时间增加约 7.5 秒。当时游戏为 720p、内部 1× 分辨率，音频服务连接正常，内存也有余量。

这些证据首先指向过热降频和模拟运算不足，但没有排除客户端或网络问题，也不能据此给所有 3DS 游戏下结论。该平台仍属于实验支持；实际兼容性和性能需要逐款检查。

## 调整顺序

1. 正常保存进度，必要时退出重型游戏，让主机降温；检查散热，再用同一场景复测。
2. 保留较低的串流尺寸和内部倍率，确认模拟器真实速度、帧时间与单线程占用。
3. 在独立测试实例中比较核心和渲染后端；记录前后结果，不直接覆盖家人的配置或存档。
4. 服务器正常后再对比局域网与域名入口、不同浏览器和设备，查看接收与播放统计。

增加音频缓冲可能减轻短暂调度抖动，也会增加声音延迟；它不能补足持续不足的模拟算力。音画同步需结合实际运行统计判断。[Libretro 音画同步指南](https://docs.libretro.com/guides/optimal-vsync/)

只更换 NVIDIA 显卡不保证解决 CPU 主线程瓶颈。RetroOne 当前的 NVIDIA 接口尚未实现完整运行链路，不能把接口预留当成已通过性能验证。不要通过改变游戏或音频速度掩盖性能不足。
